## P1: HumanEval Benchmark

### 最终结果

| Metric | Value |
|--------|-------|
| pass@1 | **148/164 (90.2%)** |
| Model | DeepSeek-chat (via CodeAgent-MCP) |
| Mode | single agent (Coder only) |
| Total time | 326s |
| 失败原因 | 16 个逻辑错误，0 个格式错误 |

### 五轮迭代调试过程

这个评测的核心挑战不是模型能力，而是**评测适配器的代码拼接问题**。HumanEval 的标准做法是 `prompt + completion` 拼接执行，但 LLM 输出格式不稳定，导致拼接后代码错位。

| 版本 | pass@1 | SyntaxError | IndentationError | 改动 |
|------|--------|-------------|-----------------|------|
| v1 | **7.3%** (12/164) | 大量 | 大量 | 初版：让模型输出 body，直接拼接 prompt |
| v2 | **35.4%** (58/164) | 24 | 65 | 加 markdown 剥离 + 签名去重 + 缩进修正 |
| v3 | **48.2%** (79/164) | 0 | 66 | 多候选拼接策略 fallback，SyntaxError 归零 |
| v4 | **54.3%** (89/164) | 0 | 63 | `normalize_indent`：dedent 到 0 再 re-indent 4 空格 |
| v5 | **90.2%** (148/164) | 0 | 0 | **思路转换**：让模型输出完整函数，直接执行 |

### 各版本问题分析与解决

**v1 → v2: 发现根因是代码拼接**
- **问题**: 模型输出被 ````python` 包裹，且重复输出了函数签名。`prompt + completion` 拼接后函数签名出现两次，产生 SyntaxError
- **解决**: 加 markdown 代码块剥离 + 用正则检测并去除重复的 `def entry_point(` 签名
- **效果**: 7.3% → 35.4%，大幅改善但仍有 89 个格式错误

**v2 → v3: 用 fallback 消除 SyntaxError**
- **问题**: 单一拼接策略覆盖不了所有输出格式（有的带签名、有的不带、有的有 import 前缀）
- **解决**: 生成多个候选拼接方式（完整函数/提取 body 后拼接/不同缩进），依次尝试执行，遇到 SyntaxError 就试下一个
- **效果**: SyntaxError 从 24 → 0，pass@1 35.4% → 48.2%

**v3 → v4: 标准化缩进**
- **问题**: 63 个 IndentationError——模型输出的缩进不统一（tab/空格混用、非4倍缩进）
- **解决**: `normalize_indent` 函数：tab 转 spaces → 找最小缩进 dedent → 统一 re-indent 4 空格
- **效果**: 仅减少 3 个 IndentationError（66→63），说明问题不是整体缩进偏移，而是代码内部缩进结构不一致

**v4 → v5: 转换思路，彻底解决**
- **问题**: 剩余 63 个 IndentationError 是模型输出的函数体内部缩进混乱（如 if 块混用 2/4 空格），无法通过后处理修复
- **关键洞察**: 之前的方案是"让模型输出 body，我们拼接"——拼接过程引入了缩进对齐问题。如果让模型输出**完整函数**（含签名），模型自己会保证内部缩进一致性
- **解决**:
  1. 修改 prompt：要求输出完整函数（不再是只输出 body）
  2. 执行策略：**先直接执行模型的完整输出 + 测试**（不拼接 prompt），失败再 fallback 到拼接候选
- **效果**: IndentationError 从 63 → 0，pass@1 54.3% → 90.2%

### 核心教训

1. **评测工具本身也需要调试**: 初版 7.3% 看起来像是模型很差，实际上是适配器有 bug。如果盲信第一次结果，会对模型能力产生严重误判
2. **后处理修不了的问题，要从源头解决**: v2-v4 都在做"修复模型输出"，收益递减。v5 转换思路——让模型输出自洽的完整代码，一步到位
3. **fallback 策略是处理 LLM 不确定性的通用模式**: 和项目中 JSON 解析的 4 层 fallback 思路一致——不要假设 LLM 输出格式固定，要准备多种解析方案

## P2: Coder 工具调用优化

### 实验设计

对比 Coder prompt 优化前后在 MCP 模式下的 token 消耗。选取 3 个代表性任务 (B1 medium, B5 hard, B6 hard)。

优化内容：在 Coder prompt 中增加工具调用效率规则：
- 不要重复读取同一个文件
- 不要用 file_search 搜索刚创建的文件
- 已知 workspace 为空时直接跳到 file_write
- 完成后简短总结，不要重复输出代码

### 结果

| 任务 | Baseline Token | Optimized Token | 降幅 | Score 变化 |
|------|---------------|----------------|------|-----------|
| B1 LRU Cache (medium) | 182,772 | 49,221 | **-73%** | 9.0 → 9.2 |
| B5 Rate Limiter (hard) | 158,252 | 397,275 | +151% | 9.5 → 8.5 |
| B6 Markdown Parser (hard) | 824,206 | 340,682 | **-59%** | 8.5 → 9.0 |
| **总计** | **1,165,230** | **787,178** | **-32%** | 持平 |

### 分析

1. **B1 效果最好 (-73%)**: 简单任务中冗余工具调用占比最高，优化后 Coder 不再重复 file_list/file_read
2. **B5 反而上升 (+151%)**: 这个任务的复杂度导致 Coder 需要更多轮修改，优化 prompt 反而让它在某些步骤犹豫更久。说明 prompt 优化不是万能的，对复杂任务可能有副作用
3. **B6 效果显著 (-59%)**: 优化后 Coder 用更少的轮次完成了 Markdown Parser（attempts 从 4 降到 2），质量反升 0.5 分
4. **总体 -32% 且质量不变**: 作为 prompt-only 优化（零代码改动），性价比极高

### 核心教训

- Prompt 优化对 token 效率的影响是显著但不均匀的——简单任务受益最大，复杂任务可能有反效果
- 优化方向应该是"减少无意义的探索"，而不是"限制工具使用次数"——后者会伤害复杂任务的表现
